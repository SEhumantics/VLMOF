\section{Tool Support}\label{sec:tool}
\subsection{Implementation and Verification}
VL-MOF\footnote{\url{https://github.com/SEhumantics/VLMOF}} accepts text declarations
or Core JSON. Figure~\ref{fig:boundary}(a) shows parsing, elaboration and checking;
JSON enters through decoding. Theorems~\ref{thm:adequacy} and~\ref{thm:checker}
connect elaboration and checking to the source semantics and conformance
relation defined in Section~\ref{sec:formalization}. Parsing and decoding are tested, not proved,
and the parser does not guarantee $A(d)$. Lean proofs use propositional
extensionality, choice and quotient soundness; execution also trusts the compiler
and runtime. Diagnostics report input, resolution and conformance failures by
condition group, without generally locating offending elements.

Figure~\ref{fig:boundary}(b) shows the Ecore/XMI import experiment. Decision boxes
compare validator outcomes; collected observations compare loaded property values.
The latter comparison receives model data, not validation results.

\subsection{Textual Notation}
Figure~\ref{fig:notation} pairs an object grammar fragment with an example.
Here \texttt{?} means optional, \texttt{*} repetition, and \texttt{qname} a name
qualified with \texttt{::}; values include literals and \texttt{@} object references.

\begin{figure}[!htbp]
\centering
\begin{minipage}[t]{.49\linewidth}\footnotesize
\textbf{Object grammar fragment}
\begin{verbatim}
object ::= "object" name ":" qname
           "{" observation* "}"
observation ::= "observe" qname
                "=" list ";"
list ::= "[" values? "]"
values ::= value ("," value)*
\end{verbatim}
\end{minipage}\hfill
\begin{minipage}[t]{.48\linewidth}\footnotesize
\textbf{Declaration and use}
\begin{verbatim}
class Sensor {}
class Route {
  requires : Sensor [2..*]
    ordered unique;
}
object s1 : Sensor {}
object s2 : Sensor {}
object r : Route {
  observe Route::requires =
    [@s1, @s2];
}
\end{verbatim}
\end{minipage}
\caption{An object grammar fragment and a complete illustrative model.}
\label{fig:notation}
\end{figure}

The example isolates Train's required-sensor relation. It declares its classes,
objects and observation; \texttt{Route::requires} names the property declaration,
while \texttt{@s1} and \texttt{@s2} name object references. Elaboration replaces
these aliases with identities and preserves the value sequence. The checker
accepts two sensors and rejects a singleton list for the lower bound of two.
Every applicable observation is explicit; scalars use singleton lists and
\texttt{[]} records an empty value sequence. The complete Train model, including
inherited observations and both opposite ends, is supplied as
\texttt{examples/train/full-v1-batch-1.dsl}.

\subsection{EMF Interchange}
VL-MOF can also check models stored by EMF. A Java bridge reads an \texttt{.ecore}
metamodel and its \texttt{.xmi} instances, converts their declarations and object
values into Core JSON, and passes that representation to the Lean checker.
The bridge assigns object identities and preserves explicitly written values
and omissions. EMF's \texttt{eIsSet} may instead treat an explicit default value
as unset, so equal validator decisions need not mean equal loaded models.
The comparison maps identities and checks classifiers, values and selected
metadata, preserving sequence order or comparing multisets as appropriate.

Import and export support the artifact's structural subset, not arbitrary EMF
features; annotations, operations and general default/unset behavior are excluded.
Export has additional ownership, naming and numeric-range restrictions. It writes
fresh Ecore/XMI with both opposites. Round-trip tests reimport those files, use an
identity sidecar to compare Core models and recheck conformance, separately from
the EMF-validator experiment.
