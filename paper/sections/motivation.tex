\section{Motivation}
Metamodeling gives different languages a shared structural foundation through
classes, inheritance, multiplicity and containment. If tools disagree on these
concepts, using the same metamodel does not ensure that they admit the same
models. A formal semantics makes these obligations explicit, supporting both
individual conformance checks and reasoning about all admitted models.

The Train Benchmark models railway networks and planned routes
\cite{szarnyas_etal_2018}. Regions contain track elements and sensors; segments
and switches form the track, sensors monitor it, and semaphores carry signals.
Routes require sensors and specify switch positions. Figure~\ref{fig:train}
shows the complete evaluated structural profile: ten classes, two enumerations
and 21 features. Italic class names denote abstract classes; diamonds mark
composition and hollow triangles inheritance. Attributes have bound $0..1$.
All features are ordered; references are unique and attributes nonunique.

A \emph{Route} requires at least two \emph{Sensor} objects, and its
\emph{follows} references must agree with the reverse \emph{route} references
of \emph{SwitchPosition} objects. Section~5 checks these structural conditions
on a model containing a route with seven required sensors.

A specification-sensitive issue appears when considering containment. Train's
\emph{Region.elements} is unique, so a repeated child is invalid. In a metamodel
allowing nonunique composite values, however, two occurrences of a child need
not imply two parents.
MOF~12.5.5 separately restricts the number of containers and the number of active
reverse container properties. Treating these as a single count of incoming
occurrences changes the accepted models. Section~3 distinguishes these obligations; separating examples in Section~5
exercise choices that Train's own declarations do not expose.
