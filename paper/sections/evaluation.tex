\section{Evaluation}
\subsection{Evidence design and reproducibility}
We distinguish universal Lean results, finite authored tests, native compatibility
observations and runtime measurements. The authored runner records repository
commit and dirty status, toolchain and Python versions, executable and input
hashes, exact commands, exit codes, standard output/error and per-case expectations.
It classifies accepted, rejected, unsupported, not-run and execution failure
separately. An unexpected outcome fails the run rather than becoming a successful
negative example.

The companion supplement \texttt{VL-MOF-review4-supplement.zip} provides
\texttt{README.md}, \texttt{INDEX.json}, the source Git bundle and this PDF.
Its \texttt{evidence/authored/} and \texttt{evidence/public/} directories contain
\texttt{results.json}, input hashes and retained command logs; \texttt{reviews/}
contains the independent assessments and fresh reproduction. The index records
full commits and file hashes. The reviewed source candidate is \texttt{4aa3bed};
the shipped revision, including review fixes, is identified in the index.
The authored measurements use \texttt{f0edde1}. The public runner and Java bridge
use \texttt{6985361}, while its checker was built at \texttt{b5e86cc}; the public
manifest identifies that executable and every bridge source by SHA-256. Its 67
commands retain resolved Maven dependencies and unchanged input hashes. Fresh
review reproduces the qualitative outcomes and structural counts at the candidate;
Table~\ref{tab:train} retains the earlier single-run timings.

The ten recorded authored cases all match their expected outcomes: three accepted,
six rejected and one unsupported wire version. They exercise JSON and DSL input,
absence versus false, occurrence typing, duplicate keys, unique and nonunique
repetition, binding failure and malformed JSON. The standard build additionally
runs five source-download tests and ten CLI test groups. The build verifies all
six pinned OMG files and compiles the imported proof modules. These are finite
checks of the implementation boundary, not samples used to infer the universal
checker theorem.

The proof-client experiment compiles an independent small client that uses
observation-key injectivity from the library: two rows of a conforming snapshot
with the same object/property key have equal occurrence lists. The client's
record includes the axiom report. This demonstrates reuse of a conformance
consequence rather than a second implementation of the checker.

\subsection{Public inputs and explicit adaptation}
Train Benchmark is pinned to commit
\texttt{6490047d7449}; the six railway XMI
snapshots share its Xcore metamodel. The original metamodel has no checked-in
generated Ecore suitable for this route. A pinned Xcore compiler produces an
intermediate Ecore, but its primitive mappings become EJavaObject and it includes
a generator annotation. A separately named adapted metamodel removes exactly
one annotation and changes three primitive mappings. The attributes \emph{RailwayElement.id}
and \emph{Segment.length} become EInt,
and \emph{Route.active} to EBoolean, using the original Xcore declarations as
source evidence. The manifest records the original annotation details, each
qualified type change and the input, output and Xcore hashes. This is an explicit
adaptation, not a claim that the compiler directly preserved the intended types.

The native snapshots omit some default enum values that their runtime interprets
as FAILURE. Separate adapted copies materialize those occurrences. Table~\ref{tab:train}
records every insertion count. A raw batch-1 control using the profile Ecore is also accepted: those enum
properties are optional. Materialization changes the represented default meaning;
it is not required to repair conformance. The original files are unchanged; object identities
are allocated independently of the ordinary \emph{id} attribute. A successful
check of an adapted file therefore means conformance of that explicit adapted
snapshot. It does not certify the omitted-value semantics of the raw original.

For each accepted Core input, the native route constructs a fresh Ecore/XMI pair,
reloads it, compares declarations and observations using its recorded identity
map, and checks the reloaded Core again. The bridge regression separately
exercises explicit false/zero/empty String/first-enum values beside absent ones,
repeated scalars, repeated reciprocal references, independent opposite ordering,
changed numeric IDs and object traversal, duplicate maps and inconsistent inverse
counts. Thus successful public round trips are accompanied by tests targeted at
semantically consequential failure modes.

EMF Compare is pinned to commit
\texttt{9f25a964c1be}. Its metamodel is rejected
for unsupported operations. Separate fixtures exercise defaults, derived
features, custom datatypes, generics and broken references. These outcomes
characterize the native boundary; none is counted as accepted EMOF compatibility.

\subsection{Answers to the research questions}
RQ1 is answered by the declarative definitions, the unconditional checker
correspondence and finite-closure completeness. Their statements apply to the
represented domain and have no empirical success-rate premise. The authored
cases demonstrate distinctions that the tools must preserve, particularly
duplicate identity versus duplicate value and absence versus explicit defaults.

RQ2 is answered by Equation~\ref{eq:adequacy}: satisfaction is specified
independently, and actual successful elaboration connects it in both directions
to checker acceptance. Lexical admissibility contains only alias conditions;
the reverse result does not assume source-model validity. The forward result
also establishes elaboration success. These proofs do not certify parsing or
imply unrestricted representation of every raw Core record.

RQ3 is answered by six accepted adapted routes, the accepted raw-XMI control
and two unsupported metamodel controls, with no failed or skipped stages.
The operational timing question is completion on these fixed inputs. Table entries
are one CLI process each, measured by Python's monotonic wall clock on WSL2/Linux,
an Intel i5-14400F and one checker binary. Import, export and compilation are
excluded. Concurrent development load was not controlled; these observations
are neither comparative benchmarks nor speedup claims.
