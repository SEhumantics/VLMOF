\section{Evaluation}
\subsection{Cases and Semantic Checks}
We use Train models and authored containment/inheritance cases. Train is the
only public positive family; the bridge rejects unchanged EMF Compare input.
The artifact records the inputs, adaptations, licenses and commands.

The source analysis in Section~3.5 answers RQ1; separating examples exercise
its bound, containment and inheritance choices. The theorems in Sections~3.3--3.4
answer RQ2. Lean checks those proofs and a client deriving nonconformance from
a duplicated link with an upper-one opposite.

The full Train input contains ten classes, 21 features, two enumerations,
754 objects and 3,378 observation rows. Its symbolic declarations parse and
elaborate to the retained Core schema and snapshot exactly, including identities,
flags, row order and recorded absence. This tests the notation path against an existing pair.
Route object~1 follows position~2, requires sensors~25--31 and references entry
and exit semaphores~425 and~34. Retaining only one required sensor causes a
multiplicity failure while the other structural checks continue to pass.

\subsection{Comparison with EMF}
The comparison pins EMF Ecore/XMI 2.39.0 and Common 2.42.0 under Java~21.
An isolated registry selects EcoreValidator for schemas and generic
EObjectValidator for dynamic instances. Diagnostician validates schema and
instance roots separately. Generated validators and OCL delegates are outside
this condition. Table~\ref{tab:correctness}(a) separates EMF's schema check,
its instance-root check, and VL-MOF's combined conformance check. ``Accept'' in
the instance column is only that call's result: it cannot override a rejected
schema. Table~\ref{tab:correctness}(b) asks whether the two tools examined the
same state by comparing mapped object identities, classifiers and property
values. A matching state can still receive different validation decisions.

The lower block of Table~\ref{tab:correctness}(a) exposes Ecore schema
restrictions. In particular, an empty $0..0$ property is permitted by our
structural interpretation but rejected by Ecore at schema level.
The repeated unique String survives loading but is accepted by this generic
validator and rejected by VL-MOF; it does not establish the behavior of every
EMF editor or generated validator. Repeated traversal of a contained object
produces duplicate collector rows in the two unpaired cases. Their alignment is
conservatively unsuccessful even though their distinct URI/value comparisons
agree; they are not timed.

The full Train v1.0 profile removes one generator annotation and maps three
primitive types. The v1.0 profile gives $0..1$ bounds to \emph{route}, \emph{target},
\emph{entry} and \emph{exit}, where the article's diagram gives multiplicity one;
Figure~\ref{fig:train} consistently uses the evaluated profile.
In the adapted batch-1 snapshot, twelve explicitly written first-enumeration
values are reported unset by native
\texttt{eIsSet}, while the lexical Core route retains \texttt{FAILURE}.
Both systems accept their respective states. This adaptation had materialized
omitted defaults and is excluded from paired timing. A fresh control using
untouched original batch-1 XMI and the explicitly adapted Ecore profile is accepted
by both validators and aligns. Zero lower bounds permit its omissions; preserving
them resolves this comparison without inserting defaults. The result is specific to this profile; the unadapted schema is unsupported.

\subsection{Validation Time}
The timing cases use the authored optional-bound Train projection, not the full
public snapshot. The deterministic workload has stars with inherited scalar features and
ordered occurrences (11/101/501 objects), Train groups (10/100/500), and
containment chains (11/101/501, depths 10/100/500), with fixed schema vocabulary.
Declaration, inheritance, observation and reference counts accompany object count.

Each case uses five independent process trials, ten warmups and thirty measured
repetitions, with both tool orders and alternate traversal directions. Builds
precede timing. We measure combined schema/instance validation on preloaded
inputs, excluding loading, serialization and diagnostics. The artifact also
records schema-only, read/decode and command-wall times. Instance-only validation
was not measured and cannot be inferred by subtracting schema time.

Table~\ref{tab:validation-times} reports the median of five process medians
in milliseconds; the artifact retains each process median, their minimum and
maximum, and all measured samples. Rows count feature observations.
